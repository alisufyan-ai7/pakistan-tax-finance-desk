## 19 Nov 2026 mobile POST Origin compatibility candidate
The owner supplied a fresh iPhone Chrome Incognito screenshot showing the sign-in failure, and confirmed the same symptom in Safari without private browsing; desktop login succeeds. A second sanitized live Railway read (19 Nov 09:10–09:13 UTC) showed desktop `POST /api/owner/login` 200; mobile `GET /owner-login` 200, `GET /api/owner/session` 401, and `POST /api/owner/login` **403** twice. This materially disfavors a stale session as the sole explanation; the actual incoming Origin header has not been inspected and is NOT conclusively identified.

Targeted source diagnosis: `frontend/owner-login.mjs` used `mode: "same-origin"` **together with** `referrerPolicy: "no-referrer"` on POST. According to the Fetch standard and MDN's `Referrer-Policy` explanation (https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Referrer-Policy#effect_on_the_origin_header), this combination may cause the browser to send `Origin: null`; the approved backend deliberately rejects `Origin` other than the exact HTTPS app origin with 403. The frontend POST helper now uses `mode: "cors"` to preserve the real Origin while keeping all endpoints path-relative, `credentials: "same-origin"`, `referrerPolicy: "no-referrer"`, secure cookie/CSRF/strict backend Origin, no local storage, no CORS authorization header and no secrets in logs. The exact metadata POST in `frontend/app.mjs` gets the same fix. GET remains `same-origin`.

This compatibility fix is **source-level and under CI/device acceptance** until confirmed: tests in `frontend/tests/mobile-origin-post.test.mjs` prevent regression; no authentic owner password/TOTP is used in tests. Do not mark Issue #193 fully resolved until the owner confirms mobile sign-in and a separate root-demo retirement is merged. No G1/G2/G3 finance/Drive permission state changed.
