# B3 — bank statement candidate source registry, synthetic only

Part of [G3 issue #29](https://github.com/alisufyan-ai7/pakistan-tax-finance-desk/issues/29) and the [owner MVP blueprint](OWNER_MVP_COMPLETION_BLUEPRINT_2026-11-16.md).

`backend/app/source_batch_evidence.py`: explicit synthetic account/legal-owner/currency/source identity, SHA-like **caller-provided fictional HMAC** (not an authenticated production source), parser revision, period, opening/running/closing balances and transaction row order. Exactly-one debit/credit, unique row IDs and bounded/ordered posting dates are required. A full running-balance chain is recomputed from the given opening balance. Exact same-source replay is idempotent; conflicting replay and same account/content with alternate ID reject. Different overlapping statement periods produce structural REVIEW_REQUIRED flags; malformed balances and quarantine states never become accepted automatically. No raw amount, date or name appears in the receipt. Missing periods remain unknown, not zeros.

**No persistence, no real bank adapter certification, no external source authenticity proof or actual ingestion.** Registry never says import/accounting accepted, even for a clean candidate. Future protected private adapter must authenticate HMAC source identity, preserve immutable originals/page-row trace, review overlaps and integrate with B2 account-month coverage and G1 protected source before accepting funds. Includes synthetic negative tests for replay, balance mismatch, overlap, legal scope, invalid row directions/dates, real-mode block.
