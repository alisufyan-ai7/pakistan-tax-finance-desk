# A5b — typed financial source-fact parity from sealed candidate

**Security / scope:** Synthetic only, G1-c Issue #21, follows [A5a read-only sealed source verification](IMPLEMENTATION_A5A_PROTECTED_CANDIDATE_PROJECTION.md). Not a live operational data model or real-data authorization.

`backend/app/canonical_fact_parity.py` first uses the **existing independently verified AES-GCM sealed candidate**, requires the complete original PostgreSQL source census and a read-only receipt, authenticates all encrypted row envelopes/HMAC identities, reconstructs full registered source rows and verifies complete-source and owner/account/July–June-year signed movements. It then builds immutable in-memory typed source facts for each bank movement (including excluded/unreviewed), confirmed transfer link, loan principal/markup allocation, cash entry, filing *source claim*, reversal event, loan and cash openings, and asset snapshot. An independently keyed domain-separated HMAC commits these interpreted source facts while the full-source HMAC still covers all audit/evidence/auth information not interpreted as economic fact.

Outputs **counts and keyed HMAC fingerprints only**; no actual money, account names, dates, raw identifiers, taxable income or source rows. All facts preserve active/inactive and original-source revisions. A filing source claim is never certified IRIS proof; unknown remains unknown.

Acceptance: complete graph, AES-GCM tamper/unknown sources, missing/extra/duplicate rows, source receipt mismatch, real-mode refusal; new smoke in the existing single PG18 job on independent restored synthetic candidate. **G1 remains blocked**: restored legacy financial tables still plaintext; no true active encrypted operational store, independently authorized cutover, key/offsite recovery, typed entity-specific balance reconciliation, private vault or real files. Next A5c/A6 is an encrypted active canonical write-side and per-domain full year-end parity after audited backup/restore; do not call this an active ledger.
